# shift-left-1-webhook-interceptor

Project 1 - a shift-left data-engineering portfolio. It demonstrates **data quality as an upstream promise** — validation pushed to the ingestion boundary and enforced automatically — using the [Open Data Contract Standard (ODCS) v3.2.0](https://bitol-io.github.io/open-data-contract-standard/) and the [Data Contract CLI](https://docs.datacontract.com/).

An ODCS data contract that blocks a breaking schema change in CI, before it ever reaches the warehouse.

[![datacontract](https://github.com/initiative1972/shift-left-1-webhook-interceptor/actions/workflows/datacontract.yml/badge.svg)](../../actions/workflows/datacontract.yml)

**The point in one line:** an upstream team drops a field from a webhook payload; this pipeline catches it in continuous integration and **blocks the merge** before the analytical warehouse is ever corrupted.

---

## The problem it solves

In a traditional pipeline, data quality is checked *after* data lands in the warehouse — by which point a silent upstream change has already propagated through your models, reports and dashboards. You find out on Friday about a break that happened on Tuesday.

This project moves the check **left**, to the boundary between an upstream producer and the warehouse. The agreement between them is a **machine-readable, versioned, executable data contract**. When a change violates the contract, CI fails and the pull request is blocked.

## Architecture

```
┌──────────────┐     ┌─────────────────┐     ┌──────────────────┐
│ mock producer│────▶│ events (JSONL)  │────▶│ DuckDB warehouse │
│  (synthetic) │     │  webhook payload│     │  table: transactions
└──────────────┘     └─────────────────┘     └──────────────────┘
        │                                              ▲
        │        ODCS v3.2.0 contract  ────────────────┘
        │        (schema + semantics + quality + SLA)
        │                      │
        └──── GitHub Actions: `datacontract test` on every PR ───┐
                                                                  │
                      ✗ breaking change  →  CI fails  →  PR blocked
```

All data is **synthetic** — generated by `src/producer.py`. There is no real, customer, or employer data anywhere in this repository.

## Quickstart (runs locally in ~2 minutes, no cloud account)

```bash
# 1. Install dependencies (ideally in a virtualenv)
#    installs datacontract-cli[all]==1.2.7 (ODCS v3.2.0 support) + duckdb
make setup

# 2. Generate synthetic transactions and load them into DuckDB
make demo

# 3. Run the data contract test against the warehouse
make test
```

> **No `make` (e.g. Windows)?** Run the steps directly:
> ```bash
> pip install -r requirements.txt
> python src/producer.py --count 1000 --out data/transactions.jsonl
> python src/load.py --in data/transactions.jsonl --db data/warehouse.duckdb
> datacontract test datacontract.odcs.yaml --server local-warehouse
> ```

`make test` should pass (green). Now break it, on purpose:

```bash
# Simulate an upstream team dropping the `currency` field from the payload
make demo-break
make test        # ❌ fails: the contract requires `currency`
```

That failure is the whole point. In CI, it blocks the merge.

## The money shot: a breaking change blocked in CI

Open a pull request that changes the producer to drop or rename a required field (or just flips the default in `src/producer.py` to `--break`). The GitHub Actions workflow runs `datacontract test`, it **fails**, and the PR is **blocked**.

## What's in the contract

[`datacontract.odcs.yaml`](datacontract.odcs.yaml) is an ODCS v3.2.0 contract. It goes beyond schema to capture:

- **Semantics** — business names and descriptions for every field, so "amount" and "currency" mean something, not just a type.
- **Quality rules** — `transaction_id` unique and non-null; `amount` within a sane range; `currency` restricted to an ISO-4217 enum; `account_id` non-null.
- **Classification** — `account_id` tagged `classification: restricted` (the hook for the CPS 234 mapping used in Project 3).
- **SLA properties** — freshness and completeness expectations.

## Regulatory mapping (CPS 230)

APRA's **CPS 230 Operational Risk Management** is **fully in force** (commenced 1 July 2025; transition ended 1 July 2026; the 30 April 2026 amendments are live). Supervisory attention has shifted to *evidence of effective implementation* of controls, not merely their existence.

A data contract at a third-party/producer boundary is a concrete example of such a control: it acts as a **technical SLA** that isolates critical analytical operations from upstream disruption, and — because it runs in CI on every change — it produces a **continuous, auditable trail** of integrity verification rather than a point-in-time attestation. See [`docs/regulatory-mapping.md`](docs/regulatory-mapping.md).

## Tech

- **Contract:** ODCS v3.2.0 (Linux Foundation / Bitol)
- **Enforcement:** `datacontract-cli`
- **Warehouse:** DuckDB (local, zero-config)
- **CI:** GitHub Actions
- **Producer:** Python (synthetic data)

## What's simplified (honest scope)

This is a focused demonstration, not a production system. Deliberately simplified: the "webhook" is a local JSONL file rather than a live Kafka/Pub-Sub stream (a streaming variant is a documented stretch goal); the warehouse is DuckDB rather than Snowflake/BigQuery; and the data volume is small. The *mechanism* — contract-enforced validation blocking breaking changes in CI — is exactly what you'd run in production.
